# Baseline measurement, NVDA 2026-01-09

**Summary (English):** Ran the team fork (TradingAgents v0.7.1 base) end to end once, measured token use and wall-clock time with the same stats callback the CLI uses, and recorded three requirement gaps the run exposed. This is the "before" row of the baseline table.

## Command

```bash
export TRADINGAGENTS_OUTPUT_LANGUAGE=English
export TRADINGAGENTS_MAX_DEBATE_ROUNDS=1 TRADINGAGENTS_MAX_RISK_ROUNDS=1
tradingagents --ticker NVDA --date 2026-01-09 \
  --analysts market,news,social,fundamentals \
  --no-checkpoint --save --html --no-show
```

Measurement was taken with `StatsCallbackHandler` driven directly, which counts every LLM call in the graph (16 in run 1, 17 in run 2); the CLI live panel reported a lower figure for the same run, because it stops redrawing before the final risk and portfolio stage.

| Run | Wall clock | Tokens in | Tokens out | Total | LLM calls | Rating | Run status | Data gaps |
|---|---|---|---|---|---|---|---|---|
| 1 | 117.6 s | 114,911 | 24,100 | 139,011 | 16 | `Overweight` | **not emitted** | `macro_data` unavailable (`FRED_API_KEY` unset), not disclosed in the report |
| 2 | 110.6 s | 116,314 | 22,468 | 138,782 | 17 | `Overweight` | **not emitted** | `macro_data` unavailable; `reddit` sentiment source returned HTTP 403; neither disclosed |

Per-call average: ~7.2k tokens in, ~1.4k out. Output is ~17-21% of the total, so cost is driven by what the agents read (analyst prompts plus tool payloads), not by what they write.

### Run-to-run variance (identical configuration)

| Measure | Run 1 | Run 2 | Spread |
|---|---|---|---|
| Total tokens | 139,011 | 138,782 | +0.16% |
| Tokens in | 114,911 | 116,314 | +1.2% |
| Tokens out | 24,100 | 22,468 | -6.8% |
| LLM calls | 16 | 17 | +1 call |
| Wall clock | 117.6 s | 110.6 s | -6.0% |

Two consequences for the baseline:

1. **Token totals are stable enough to quote as one figure** (~139k for this configuration): a 0.16% spread across runs means the number is a property of the configuration, not of the run.
2. **Call count and wall clock are not stable.** An extra LLM call appeared in run 2 with no configuration change, so latency must always be reported as a range or an average over several runs, never as a single value. Token composition also shifts (in up versus out down) even when the total holds, which is why both halves are recorded separately.

## Gaps observed (evidence for the requirement work)

1. **No run status.** The report header shows `Rating: Overweight` and nothing else. There is no `COMPLETE` / `INCOMPLETE(reason)` field anywhere, so a run that lost a data channel is indistinguishable from a clean one.
2. **No separate action field.** The trader's Buy/Hold/Sell appears only inside prose; the rating is the only labelled decision field in the header, so a reader cannot tell a research opinion from a proposed action.
3. **Silent data gap.** `macro_data` was unavailable for the whole run. The only trace is a log warning; the report never says the channel was missing, so a reader sees a complete-looking analysis. Run 2 also lost the Reddit sentiment source to `HTTP 403`, with the same silence.

These are the baselines for `REQ-TA-RUN-001`, `REQ-TA-FR-006` and `REQ-TA-FR-005` respectively.

## Anomalies observed

- Macro lookups failed six times in one run and once per analyst afterwards; the framework labels the channel "Optional" and proceeds. This is the mechanism by which a degraded run looks complete.
- Reddit sentiment fetch returned `HTTP 403` (unauthenticated request). The sentiment analyst produced a report anyway, with no note that social data was missing.
- Report timestamp uses run time, not the analysis date: a run executed on 2026-11-13 analysing 2026-01-09 is stamped `Generated: 2026-11-13`, while the analysis date appears separately. Any record that only quotes the folder name will mis-describe the analysed period.
